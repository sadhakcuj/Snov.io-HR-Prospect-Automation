A step-by-step n8n automation integrating the Snov.io API to search for HR professionals in Hyderabad.

# Snov.io HR Prospect Automation Using n8n

## 1. Project Overview

This project uses n8n to integrate with the Snov.io API and search for HR and Talent Acquisition professionals located in Hyderabad, Telangana, India.

The workflow uses HTTP requests to authenticate with Snov.io, search for prospects, and retrieve the search results.

## 2. Node 1: Snov - Get Access Token

### Purpose

This node authenticates the application with Snov.io and obtains an access token. Subsequent nodes use this token to authenticate their API requests.

### Configuration

| Setting | Value |
|---|---|
| Node Type | HTTP Request |
| HTTP Method | POST |
| URL | `https://api.snov.io/v1/oauth/access_token` |
| Authentication | None |
| Send Body | Enabled |
| Body Content Type | Form URL Encoded |

### Body Parameters

The request contains three parameters:

**1. `grant_type`**

Value: `client_credentials`

Specifies the OAuth 2.0 authentication flow. This flow allows an application to request an access token using its own credentials.

**2. `client_id`**

Value: My Snov.io API User ID.

Identifies the registered API client requesting access. It does not independently prove that the application is authorised.

**3. `client_secret`**

Value: My Snov.io API Secret.

A confidential credential associated with the API client. It helps Snov.io authenticate the application and must be kept private.

### Why POST?

POST is used because the Snov.io access-token endpoint expects authentication parameters to be submitted in a POST request.

The server processes the request and returns a response. A separate GET request is not required to receive the access token.

### Why Form URL Encoded?

This setting tells n8n how to format the request body. The parameters are sent as form-encoded data, as expected by the token endpoint.

### Authentication: None

The HTTP Request node's built-in authentication setting is set to None because the credentials are supplied manually in the request body.

Snov.io still validates these credentials. None does not mean that the API request is unauthenticated.

### How the Node Works

1. n8n sends a POST request to the Snov.io access-token endpoint.
2. The request includes the grant type, client ID, and client secret.
3. Snov.io validates the application credentials.
4. If authentication succeeds, Snov.io returns an access token.
5. n8n makes the response available to subsequent nodes.

### Output

The response includes an `access_token` field and may include an `expires_in` field indicating the token's validity duration in seconds.

The token is a separate credential returned by Snov.io; it is not the same as the client ID or client secret.

### Passing the Token to Another Node

The token can be accessed using this n8n expression:

```javascript
{{ $node["Snov - Get Access Token"].json["access_token"] }}
```

This expression retrieves the access token from Node 1's JSON output.

### Key Learnings

- HTTP methods and API endpoints.
- OAuth 2.0 Client Credentials flow.
- Request bodies and form URL encoding.
- Application identification versus authentication.
- API responses and access tokens.
- Passing data between n8n nodes.

## Node 2: Search HR Prospects

### Purpose

The purpose of this node is to initiate a search in the Snov.io database for HR and Talent Acquisition professionals located in Hyderabad, Telangana, India.

This node sends the search criteria to Snov.io and receives a task identifier (`task_hash`) that is used by Node 3 to retrieve the results.

### Configuration

| Setting | Value |
|---|---|
| Node Name | `Snov - Search HR Prospects` |
| HTTP Method | `POST` |
| URL | `https://api.snov.io/v2/database-search/prospects/start` |
| Authentication | None |
| Body Content Type | JSON |
| Send Body | Enabled |

### Request Body

The request body contains the access token, requested page and prospect filters.

```javascript
{{ JSON.stringify({
  access_token: $node["Snov - Get Access Token"].json["access_token"],
  page: 1,
  filters: {
    prospect: {
      job_titles: {
        include: [
          "HR Manager",
          "Human Resources Manager",
          "Talent Acquisition",
          "Talent Acquisition Specialist",
          "Recruiter",
          "HR Business Partner"
        ]
      },
      departments: {
        include: ["human_resources"]
      },
      locations: {
        include: {
          locality: {
            locality: "Hyderabad, Telangana, India",
            location_type: "city"
          },
          location_type: {
            locality: "Hyderabad, Telangana, India",
            location_type: "city"
          }
        }
      }
    }
  }
}) }}
```

### Explanation of the Request Body

- **`access_token`**: Dynamically retrieves the access token generated by Node 1. This avoids manually copying the token into the request.
- **`page: 1`**: Requests the first page of prospect results.
- **`filters`**: Contains the search criteria used to narrow down the prospects.
- **`job_titles.include`**: Specifies the job titles to target, including HR Managers, Recruiters and Talent Acquisition professionals.
- **`departments.include`**: Restricts the search to prospects classified under the Human Resources department.
- **`locations.include`**: Specifies Hyderabad, Telangana, India as the target location.
- **`JSON.stringify()`**: Converts the JavaScript object into JSON text accepted by the configured n8n request body field.

The location filter uses the nested structure that was tested successfully in this workflow.

### Why POST?

The endpoint is designed to start a new prospect-search task. POST sends the search criteria to Snov.io so that it can process the request.

Using POST does not mean that the response cannot contain data. In this case, the endpoint returns information about the search task rather than necessarily returning the completed prospect list immediately.

### Expected Output

The response includes task metadata, including a `task_hash` that identifies the search task.

Node 3 uses this identifier to retrieve the corresponding prospect results.

### Key Concepts Learned

- HTTP methods are selected according to the operation supported by an endpoint.
- n8n expressions allow data from one node to be reused in another.
- Search filters narrow down the target prospects.
- Asynchronous processing separates starting a task from retrieving its results.
- A task identifier connects the initial search request to the subsequent results request.

## Node 3: Get Prospect Results

### Purpose

The purpose of this node is to retrieve the prospect records associated with the search task initiated by Node 2.

Instead of starting another search, this node uses the `task_hash` returned by Node 2 to request the corresponding results from Snov.io.

### Configuration

| Setting | Value |
|---|---|
| Node Name | `Snov - Get Prospect Results` |
| HTTP Method | `GET` |
| URL | Dynamically generated using the `task_hash` from Node 2 |
| Authentication | None |
| Query Parameter | `access_token` |

### URL Expression

```javascript
{{ 'https://api.snov.io/v2/database-search/prospects/result/' + $node["Snov - Search HR Prospects"].json["meta"]["task_hash"] }}
```

### Explanation of the URL Expression

- **Base URL**: Specifies Snov.io's prospect-search results endpoint.
- **`$node["Snov - Search HR Prospects"]`**: References the output of Node 2.
- **`.json["meta"]["task_hash"]`**: Extracts the task identifier from Node 2's response.
- **`+` operator**: Joins the base URL and the task identifier into a complete URL.

The URL is generated dynamically so that Node 3 uses the task identifier returned by the current search execution, rather than a manually entered or potentially outdated identifier.

### Query Parameter

| Parameter | Value |
|---|---|
| `access_token` | `{{ $node["Snov - Get Access Token"].json["access_token"] }}` |

The access token is retrieved dynamically from Node 1 and supplied as a query parameter.

Node 3 requires authentication independently of Node 2 because it makes a separate HTTP request.

### Why GET?

The endpoint retrieves the results of an existing search task. GET is appropriate because the operation reads data rather than initiating a new search.

The distinction between the two nodes is:

- **Node 2 (POST)**: Starts the search task.
- **Node 3 (GET)**: Retrieves the results associated with that task.

The HTTP method alone does not determine whether an operation is synchronous or asynchronous. That behaviour depends on the API endpoint's design.

### Expected Output

The response contains prospect data and pagination metadata. Depending on the response, relevant fields include:

- `data.total`: The total number of matching prospects reported by the API.
- `data.page`: The page represented by the response.
- `data.total_pages`: The total number of result pages reported by the API.
- `data.prospects`: The collection of prospect records returned in the response.

Individual prospect records may contain names, job titles, locations, company information, LinkedIn URLs and email-reveal URLs.

The reported total does not mean that every matching prospect has been returned in a single response. The actual records returned depend on the requested page and the API account's applicable limits.

### Key Concepts Learned

- A task identifier links a search request to its results.
- Expressions can dynamically construct URLs using data from earlier nodes.
- Query parameters provide additional information required by an API endpoint.
- Authentication must be provided for each request according to the endpoint's requirements.
- Arrays such as `data.prospects` can contain multiple records for subsequent processing.
- Pagination metadata must be distinguished from the actual records returned.

## Current Workflow Summary

The first three nodes establish the authentication and prospect-search pipeline:

1. **Node 1 — Get Access Token:** Authenticates the application and obtains an access token.
2. **Node 2 — Search HR Prospects:** Starts a search for HR and Talent Acquisition professionals matching the configured criteria.
3. **Node 3 — Get Prospect Results:** Retrieves the prospect records associated with the search task.

### Planned Next Steps

The next stage of the project will focus on:

- Filtering and reviewing relevant prospects.
- Selecting suitable contacts before revealing email addresses.
- Retrieving and, where supported, verifying professional email addresses.
- Removing duplicate records.
- Saving the selected contact details to Google Sheets.
